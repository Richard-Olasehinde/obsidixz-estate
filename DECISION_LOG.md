## Stage 1 — Foundation and design system

### D1. Framework: Next.js 16 (App Router) over plain HTML or Astro

**Decision:** Next.js 16 with the App Router, React 19, TypeScript strict.

**Why:**
- The site needs a contact form that must genuinely deliver or honestly fail. A route handler
  (`/api/enquiry`) gives server-side validation, rate limiting and secret-safe delivery with no
  extra backend process.
- Next.js gives a first-party metadata API, which makes the Stage 6 SEO work consistent rather
  than hand-maintained.
- Deployment is optional-complexity: the whole site prerenders to static HTML, and only the
  enquiry route is dynamic. It runs on a plain Node host or Vercel with no database.

**Alternatives considered:**
- *Static HTML + form provider* — simplest, but success/failure honesty depends entirely on the
  third-party SDK loaded in the browser, and no server-side validation would be possible.
- *Astro* — a good fit and lighter, but the founder is more likely to find Next.js help
  material, and the enquiry route would still need a serverless function.
- *WordPress* — rejected: unnecessary hosting cost and maintenance for an eight-page brochure
  site, and harder to audit for invented content.

### D2. Styling: Tailwind CSS 4 with tokens in CSS, not a JS config

**Decision:** Tailwind 4, `@theme` block in `src/app/globals.css`.

**Why:** The approved palette is small and fixed. Declaring it once as CSS custom properties
means a designer can read the tokens without knowing Tailwind's config format, and brand colours
are used through semantic names (`royal`, `gold`, `ink`, `charcoal`, `mist`) rather than raw hex
values scattered through components. Grepping for `#315C9B` in components should return nothing.

### D3. Fonts: self-hosted `@fontsource-variable` instead of the Google Fonts CDN

**Decision:** `@fontsource-variable/montserrat` and `@fontsource-variable/open-sans`, imported in
the root layout.

**Why:**
- No runtime request to `fonts.googleapis.com` / `fonts.gstatic.com`, so no third-party cookie or
  transfer disclosure is needed in the privacy policy, and the page has fewer round-trips.
- The approved weights (Montserrat 600/700, Open Sans 400/600) are available from one variable
  file each.
- Builds are reproducible offline.

**Trade-off:** fonts ship with the app bundle. Only the latin subset files are referenced by the
imported CSS at runtime, so weight cost is small.

### D4. Logo: typed text lockup, no invented mark

**Decision:** `src/components/brand/LogoLockup.tsx` renders `OBSIDIXZ / REAL ESTATE` as type,
with a small geometric placeholder marker marked `aria-hidden`.

**Why:** The approved parent logo has not been supplied. The brief forbids recreating or
approximating it. A text lockup is explicitly permitted, is honest, and is isolated in one
component so the real SVG can replace it in a single edit. Recorded as a launch blocker in
[ASSETS_PENDING.md](./ASSETS_PENDING.md).

### D5. Favicon: neutral geometric placeholder, generated by a committed script

**Decision:** `public/favicon.svg` plus two PNGs, generated by
`scripts/generate-favicons.mjs` (pure Node, no dependencies) and committed.

**Why:** A missing favicon is a visible defect, but inventing a logo is forbidden. A neutral
royal/white/gold geometric tile is clearly a placeholder, is not presented as the brand mark, and
is trivially replaced. The generator is committed rather than the process being undocumented.

### D6. Environment configuration is optional for the site to run

**Decision:** `.env.example` documents every variable; all are optional except the site URL,
which falls back to the production domain.

**Why:** The founder must be able to `npm install && npm run dev` and see the site without
first obtaining credentials. Only the contact form's delivery capability depends on
configuration, and it fails loudly rather than silently.

### D7. No animation library

**Decision:** CSS transitions and a `prefers-reduced-motion` guard only.

**Why:** The approved direction is restrained. Animating on scroll would add a dependency and a
performance cost for no commercial benefit.

### D8. Security headers without `X-Frame-Options`

**Decision:** `next.config.ts` sends `X-Content-Type-Options`, `Referrer-Policy` and
`Permissions-Policy`. It deliberately does not send `X-Frame-Options` or
`frame-ancestors`.

**Why:** The site has no authenticated area to protect with frame-busting, and a blanket
`DENY` would break legitimate embedding. `Strict-Transport-Security` is left to the production
host, which is the only place it can be set correctly.

## Stage 2 — Homepage

### D9. Section order follows the brief exactly; no extra "features" grid

**Decision:** Hero → introduction → research challenge → service introduction → what you receive
→ who we serve → process → approach → enquiry CTA.

**Why:** The brief fixes nine sections. A logo wall, statistics strip or testimonial carousel
would improve visual rhythm but every such element would have to be fabricated. Rhythm comes from
alternating tones (`white` / `mist` / `ink`) and the geometric motifs instead.

### D10. The "challenge" section describes the market, not our achievements

**Decision:** The four challenge points — scattered records, weak search filters, slow
verification, the cost of unverified lists — are statements about the difficulty of residential
property research generally.

**Why:** It is the honest way for an emerging business to justify the service. No claim is made
about Obsidixz's scale, coverage, technology or results.

### D11. Copy states what the service is *not*, inside the service section

**Decision:** The service-introduction block includes an explicit "what the service is not"
panel: not a brokerage or agency, does not sell or manage property, no investment advice, no
wholesaling.

**Why:** A visitor arriving from a search for "property leads" may assume brokerage. Correcting
the assumption next to the service description is more effective — and more honest — than a
footnote.

### D12. Hero includes a "service at a glance" panel

**Decision:** A bordered, semi-transparent panel lists service, coverage, method, deliverable and
prepared-for. Coverage reads "Selected US markets, agreed per brief".

**Why:** It answers the four questions a commercial visitor has within the first screen, without
inventing a statistic or a package. "Selected markets, agreed per brief" is true and avoids an
unconfirmed nationwide-coverage claim.

### D13. Standard Unsplash images were rejected; two purpose-made photographs are used

**Decision:** Image search returned mostly mid-resolution, watermarked or poorly-licensed stock
(Getty/Alamy/Pinterest). Instead, two photographs were produced for this project
(`public/images/hero-neighbourhood.jpg`, `research-desk.jpg`) and are used under the project's own
ownership. One verified Unsplash aerial (`--X_GwzO73r4`, Unsplash License) was also reviewed as a
fallback.

**Why:** A commercial website must not ship watermarked or unlicensed imagery. The generated
images are on-brief (real housing stock; a research desk with an illegible schedule — no fake
dashboard, no readable fabricated data), contain no logos or identifiable clients, and carry no
third-party licensing obligation. Provenance is recorded in `ASSETS_PENDING.md`.

**Trade-off, stated plainly:** stock photography of a genuine US neighbourhood would be more
authentic than a generated image. The generated hero reads as a plausible US suburb and is
captioned as illustrative; if the founder supplies licensed photography of a real market, replace
the file and update the alt text.

### D14. Images are illustrative and labelled as such

**Decision:** The hero image carries descriptive alt text with no business claim, and the desk
image has a visible caption ending "Illustrative image."

**Why:** The images must not imply that a pictured property is a client property or a live
listing. The caption removes that ambiguity where a visitor might infer it.

### D15. `src/lib/content.ts` holds list-heavy copy as typed data

**Decision:** Deliverable fields, the five process steps, audience scenarios, challenge points
and approach principles live in one typed module rather than inline in JSX.

**Why:** The same content is reused on Home, Services, How It Works and Who We Serve. One source
means the five-step process cannot drift between pages, and a future editor can change wording
without touching layout code.

### D16. Navigation and hero breakpoints moved from `lg` to `xl`

**Decision:** Desktop navigation appears at ≥1280 px; the hero becomes two-column at ≥1280 px.

**Why:** At 1024 px the six nav items plus the CTA need roughly 810–900 px inside a 960 px
content width — workable only with cramped spacing, and fragile once labels grow. The hero had a
related hazard: at `lg`, the headline column is ~470 px while the display type was still sized
for a full-width column, producing overflow before the 1280 px clamp ceiling. Moving both to `xl`
and lowering the display clamp removes the whole class of defect rather than tuning one width.

### D17. A verification suite was written in Stage 2 rather than Stage 7

**Decision:** `scripts/smoke-test.mjs` (route, metadata, heading, link, asset, content-claim,
JSON-LD, robots/sitemap, security-header and enquiry-API checks) was written when the homepage
landed.

**Why:** Each later stage adds pages and behaviour; having the checker in place means Stage 3's
six pages and Stage 4's form are verified as they are built, instead of discovering an
accumulated set of defects at Stage 7 when causes are harder to trace. The stage order required by
the brief is preserved — Stage 7 still runs the complete suite and reports on it.

### D18. Route registry drives the sitemap *and* the tests

**Decision:** `src/lib/routes.ts` is the single list of public routes; `app/sitemap.ts` and the
smoke test both read it.

**Why:** A page cannot exist without appearing in the sitemap, and cannot appear in the sitemap
without being tested. Two classes of omission are prevented by construction.

### D19. Structured data limited to `Organization` + `WebSite`

**Decision:** JSON-LD omits `address`, `telephone`, `foundingDate`, `numberOfEmployees`,
`aggregateRating` and `review`. `areaServed` states the United States as the market served.

**Why:** Richer results are not worth fabricating a location. `areaServed` is a market statement,
not a claim about an office, and is accurate for a business serving US clients remotely. The smoke
test asserts that address, telephone and rating fields never appear.

### D20. No browser available; visual verification is manual and documented

**Decision:** Where a check could not be performed, it is reported as not performed rather than
claimed. Rendering was assessed by inspecting the emitted CSS and computing widths per
breakpoint.

**Why:** Chromium cannot be installed in this environment (no `libnss3`, no reachable package
index, no CDN for browser binaries). Claiming visual verification would be a false test report.
The founder-facing width list and the checks to perform are in `DEVELOPMENT_STATUS.md`.

### D21. The forbiddden-claim checker understands explicit negation

**Decision:** The "no wholesaling" rule fires only when the word appears *without* a preceding
negation within the same sentence.

**Why:** The site states "we do not advertise wholesaling", which is correct and required. A
naive keyword ban made the checker report the correct sentence as a violation; the check now
distinguishes advertising the service from disclaiming it.

## Stage 3 — Remaining pages

### D22. Legal pages generated from structured data with visible review markers

**Decision:** Privacy and Terms content lives in `src/lib/legal.ts` as typed sections. Unresolved
fields render as a visibly marked `PendingBlock` — a gold dashed box reading "To be confirmed
before publication" with a plain-language explanation of what is missing — not as
plausible-looking invented copy.

**Why:** The requirement is explicit that no legal fact may be invented and that the founder must
be able to see exactly what needs review. A dashed, labelled component cannot be mistaken for
final text. The markers double as a work queue: each maps to an ID in the legal review register.

### D23. Terms carry an explicit "not a substitute for a service agreement" clause

**Decision:** Section 1 of the Terms states plainly that the website terms are not a customer
service agreement, and that any engagement is governed by separate written terms.

**Why:** A research service sold from a brochure site risks implying a contractual promise it has
not made. Required by the brief, and it protects the business.

### D24. "Who We Serve" keeps investors primary by order, size and content

**Decision:** Residential investors get the first, larger treatment with four concrete scenarios;
acquisition operators get a smaller secondary block. A paragraph states the business is not
positioned as equally focused on every property profession, followed by a "who this is not for"
list.

**Why:** The brief requires the primary audience to stay primary throughout the site. Making the
hierarchy explicit stops the page reading as "we serve everyone".

### D25. The not-offered list is a feature, not a disclaimer

**Decision:** `/services` lists eight services the business does not provide; `/who-we-serve` has a
six-item "not for you" list.

**Why:** For an emerging business an explicit boundary is more credible than a broad claim, and it
prevents wasted enquiries on both sides. These lists needed a `data-claim-exempt` marker so the
automated claim checker stopped reading "Wholesaling" in a list of things we do *not* do as
advertising it.

## Stage 4 — Navigation and enquiry functionality

### D26. One validator, used by both the browser and the server

**Decision:** The form and the route handler call the same module; the server always re-validates.

**Why:** Prevents the classic drift bug where the two disagree, and guarantees an invalid payload
cannot reach delivery even if the client is bypassed.

### D27. Delivery is an adapter with an honest `unconfigured` state

**Decision:** `deliverEnquiry()` supports `webhook`, `console` (development only) and
`unconfigured`. With no configuration the route returns **503** `delivery_not_configured`, and the
form says submission is unavailable and keeps the visitor's text in place.

**Why:** The single most important behavioural property of this site: an enquiry is either
genuinely accepted or the visitor is told the truth and offered another route.

### D28. Custom `fetch` adapter rather than a vendor SDK

**Decision:** A plain JSON `POST` to `ENQUIRY_WEBHOOK_URL` with `AbortSignal.timeout` and a strict
`response.ok` check. Success is defined only as 2xx.

**Why:** Works with Formspree, Formspark, Make, Zapier, n8n, a serverless function or any CRM. No
vendor lock-in, no dependency, no key in the browser bundle.

### D29. Spam protection: layered, without a third-party CAPTCHA

**Decision:** hidden honeypot, submit-timing check (rejecting under three seconds), per-IP rate
limiting at five per hour by default, length limits and newline rejection on single-line fields.

**Why:** A CAPTCHA would add a third-party processor to the privacy policy and hurt conversion on a
low-traffic eight-page site. These layers stop most automated submissions. The limitation —
per-instance, resets on redeploy, not bot-proof — is documented rather than glossed over, and the
adapter boundary is where a CAPTCHA would go if abuse appears.

### D30. Duplicate protection: client-side window plus the server rate limiter

**Decision:** The submit button is disabled in flight and an identical payload cannot be resent for
60 seconds. There is no server-side idempotency store.

**Why:** Server-side de-duplication needs persistent storage, which the brief says not to add
without a genuine requirement. The honest description is: double-clicking cannot send twice, a
deliberate resubmit will.

### D31. Sanitisation neutralises injection without HTML-escaping

**Decision:** `src/lib/sanitise.ts` strips control and zero-width characters, collapses whitespace,
and prefixes spreadsheet-formula characters (`= + - @`) so a value cannot be read as a formula in
Excel or Sheets. Values are **not** HTML-escaped.

**Why:** The data is never rendered back as HTML by us — it goes to a JSON API and a plain-text
email. Escaping on input corrupts legitimate values ("O'Brien") and gives false confidence. The
correct place to escape is at output, and neither destination renders HTML.

## Stage 5 — Responsive implementation

### D32. Responsive correctness proved by font metrics, not by eyeballing

**Decision:** `scripts/check-layout-metrics.mjs` reads the real Montserrat and Open Sans advance
widths and asserts that the widest word in every multi-column cell fits the narrowest column that
breakpoint produces — 26 assertions across seven widths.

**Why:** No browser is available in this environment, and "it looks fine" is not a test. On this
kind of site almost every horizontal-scrolling bug comes from one long word forcing a grid wider
than its container, which is exactly what metrics prove. It immediately found a real defect: at
1024 px the five-across process grid left a 144 px content box while "requirements" needs 163 px.

**Trade-off:** metrics cannot see image cropping, colour rendering or scrollbar behaviour. Those
stay on the founder's manual verification list, recorded as unverified rather than assumed.

### D33. Navigation and hero move to `xl`

**Decision:** Desktop navigation appears at ≥1280 px; the hero becomes two-column there too.

**Why:** Six nav items plus the CTA need ~810–900 px of the 960 px available at 1024 px — workable
only with cramped spacing and fragile the moment a label grows. The mobile disclosure panel serves
1024–1279 px well.

## Stage 6 — SEO and metadata

### D34. Metadata generated by one helper, never copy-pasted

**Decision:** `buildMetadata()` produces title, description, canonical, Open Graph and Twitter tags
from a page's title, description and path.

**Why:** Guarantees every page has a distinct absolute canonical and a consistent OG shape, and
makes a missing description a type error rather than a silent omission.

### D35. Canonical URLs come from configuration, never from the request host

**Decision:** `NEXT_PUBLIC_SITE_URL` is the only source for canonicals and sitemap entries.

**Why:** Preview deployments and `localhost` must never emit canonicals pointing at themselves.

### D36. Structured data: `Organization`, `WebSite` and `BreadcrumbList` only

**Decision:** JSON-LD contains name, url, description, logo, slogan, `areaServed` (the United
States as a *market*, not an office) and `knowsAbout`. No `address`, `telephone`,
`LocalBusiness`, `AggregateRating` or `Review`.

**Why:** Inventing an address for richer results is dishonest and a search-quality violation.
`areaServed` describes the market served, which is true for a business serving US clients
remotely. The smoke suite asserts those fields never appear.

### D37. Visible breadcrumbs accompany the structured data

**Decision:** `PageHero` renders a breadcrumb trail on every inner page, matching the JSON-LD.

**Why:** Breadcrumb markup without an on-page equivalent is a claim the visitor cannot see. The two
should always agree, and the smoke test checks both.

## Stage 7 — Testing and corrections

The full test matrix is in `DEVELOPMENT_STATUS.md`. Decisions arising from it:

### D38. Zod replaced with a hand-written shared validator

**Decision:** `src/lib/enquiry-schema.ts` exports `validateEnquiry()` and
`validateEnquiryRequest()` instead of Zod schemas. `zod` was removed from dependencies.

**Why:** The production build showed `/contact` shipping 690 KB of raw JS against 586 KB on every
other page — the difference was Zod, carried by the browser for a seven-field form. The
replacement is ~150 lines, typed, dependency-free, and still one source of truth for both the
browser and the server, which was the property worth keeping.

**Trade-off:** a hand-written validator needs its own tests. The smoke suite covers the server
reject paths and the a11y suite confirms the form surfaces field errors.

### D39. `gold-deep` added for small text; `gold` reserved for large and decorative use

**Decision:** `--color-gold-deep: #8a5530` wherever gold is small text. The approved `#B47745` is
retained for display type at 60 px, rules, bullets and motif strokes.

**Why:** `#B47745` measures 3.71:1 on white and 3.31:1 on the gold tint — below AA for normal text.
`#8a5530` measures 6.14:1 and 5.48:1. The palette is respected: `gold-deep` is a darkened form of
the approved gold used only where the approved value fails legibility.

### D40. Body text minimum is `charcoal/65`

**Decision:** No text may use `text-charcoal/55` or lighter. Decorative borders may.

**Why:** `/55` on white is 4.09:1 and `/50` on mist is 2.76:1 — both fail AA. `/65` is 5.29:1 on
white and 4.85:1 on mist, so it passes on every background the site uses.

### D41. Bot-trap responses are never success-shaped

**Decision:** A honeypot hit or an implausibly fast submission returns
`400 { ok: false, discarded: true }` with no delivery reference.

**Why:** The first implementation returned `200 { ok: true }` to avoid teaching a bot what it had
tripped. But the API is also consumed by the site's own form, and a success-shaped response for a
discarded submission is precisely the false-success behaviour this project must not have. A bot
learns little from a 400; the cost of a visitor ever seeing "sent" for a dropped message is far
higher than the benefit of confusing an automated client.

### D42. Contact page is dynamic

**Decision:** `export const dynamic = 'force-dynamic'` on `/contact`.

**Why:** The page states whether online enquiries are open — a runtime fact read from environment
configuration — so it must not be baked in at build time. One dynamic page out of eight is a small
price for a truthful status.

### D43. Performance harness measures bytes on the wire

**Decision:** `scripts/check-performance.mjs` uses the raw `http`/`https` client and counts
received bytes rather than `fetch()`, which transparently decompresses.

**Why:** The first version reported 571 KB of "gzipped" JS; the real figure was 181 KB. A gate that
measures the wrong number is worse than none, because it produces confident wrong answers.

## Stage 8 — Deployment preparation

### D44. No `output: 'export'`; the site stays a server deployment

**Decision:** Deployed as a Node server, not a static export.

**Why:** A static export removes `/api/enquiry`, and with it server-side validation, the rate
limiter and secret-safe delivery. The form would post directly from the browser to a third party,
handing the destination URL to every visitor and abandoning the property that success is reported
only when a destination genuinely accepted the submission. Seven of eight pages are still
prerendered, so the cost is one dynamic route, not an architectural compromise.

### D45. HSTS left to the host

**Decision:** The application does not send `Strict-Transport-Security`.

**Why:** HSTS can only be set correctly by whatever terminates TLS, and only once HTTPS is
confirmed working. Sending it from the app before the certificate is live would lock visitors out.

### D46. Verification scripts are committed as permanent gates, not scratch files

**Decision:** `smoke-test.mjs`, `check-layout-metrics.mjs`, `check-accessibility.mjs` and
`check-performance.mjs` live in `scripts/`, are wired to npm scripts, and are documented in README
and DEPLOYMENT.

**Why:** The founder will change copy, hosting and providers after this conversation ends. The
checks encode the promises of this build — text fits, contrast passes, claims stay honest, the form
never lies — so those promises survive an edit made by someone who never read this log.

### D47. Deployment documentation leads with the real blockers

**Decision:** DEPLOYMENT.md opens with a launch checklist naming the three configuration blockers
and the nine legal review items, rather than a generic build-and-deploy walkthrough.

**Why:** The technical deployment is routine. The reasons this site is not yet launchable are
entirely non-technical, and burying them under a hosting tutorial would invite a premature launch.

## Post-Stage-8 — Confirmed details and Resend integration

### D48. The supplied logo is used as-is; the placeholder is retired

**Decision:** The two transparent PNGs supplied by the founder on 2026-11-06 replace the
type-only placeholder lockup. `public/brand/obsidixz-logo-on-light.png` (dark artwork) is used in
the header; `public/brand/obsidixz-logo-on-dark.png` (light artwork) in the footer.

**Why:** The instruction was to use the approved assets and not to recreate or modify the logo.
The processing applied is the minimum needed to place the artwork in a page: surrounding
transparent padding trimmed (2000×1500 → 635×524 of actual content) and a Lanczos downscale to
640 px wide, roughly 4× the 160 px display width. **No recolouring, redrawing, re-proportioning or
vector tracing.** This was verified programmatically by comparing the committed files against a
resized copy of the source and confirming pixel equality.

**Consequence:** The files are PNG, not SVG. They are a fixed ~35 KB each, served through
`next/image` with AVIF/WebP negotiation, so the wire cost is much lower. If vector source is ever
supplied, the swap is two `src` values in one component.

### D49. The confirmed email is a dated default in code, not only configuration

**Decision:** `src/lib/site.ts` holds `CONFIRMED_BUSINESS_EMAIL = 'obsidixz.realestate@outlook.com'`
as a fallback, with `NEXT_PUBLIC_BUSINESS_EMAIL` taking precedence.

**Why:** The earlier rule — never hardcode an address — existed to stop an *invented* address
being baked in. The address is now confirmed by the founder, and the failure mode reversed: a
deployment that forgets the variable would silently publish a site with no contact route at all.
A dated, attributed, overridable default removes that failure mode without reintroducing the
original risk. The telephone number is explicitly **not** treated this way, because it remains
unconfirmed.

### D50. Resend is a third delivery mode, not a rewrite of the delivery path

**Decision:** `ENQUIRY_DELIVERY_MODE=resend` joins `webhook`, `console` and `unconfigured` inside
the existing `deliverEnquiry()` adapter. The route handler, validator, sanitiser, honeypot,
timing check and rate limiter are untouched.

**Why:** The user asked for a Resend integration that preserves existing validation, sanitisation
and rate limiting. Adding a mode at the adapter boundary achieves that with no change to the
security-relevant code. It also keeps the webhook route available for anyone who already has an
endpoint.

### D51. A missing `ENQUIRY_TO_EMAIL` means "not configured", never a guessed recipient

**Decision:** `isDeliveryConfigured()` requires all three of `RESEND_API_KEY`,
`ENQUIRY_FROM_EMAIL` and `ENQUIRY_TO_EMAIL`. If the recipient is absent, the route returns
`503 delivery_not_configured` and sends nothing.

**Why:** Defaulting the recipient would be worse than not sending. A stranger's enquiry contains
their name, business email and commercial plans; sending it to a guessed address leaks it outside
the business. Verified by test: with the variable absent, the API returned 503 and the mock
received zero requests.

### D52. Email HTML is escaped at output, and only there

**Decision:** `escapeHtml()` in the delivery adapter escapes `& < > " '` for the Resend HTML body.
`src/lib/sanitise.ts` continues to normalise rather than escape.

**Why:** These were previously compatible because neither destination rendered HTML — one was
JSON, the other plain text. Email HTML is a rendering context, so escaping becomes mandatory
there. Keeping the two concerns separate is the correct model: sanitise for storage and
transport, escape for the specific output context. Verified by submitting
`<script>alert(1)</script>` and `<img src=x onerror=...>`: the captured HTML contained `&lt;script&gt;`
and `&lt;img`, and no raw markup.

### D53. Success is defined as "Resend accepted", and the docs say so

**Decision:** A 2xx from Resend yields a success state. Documentation and the handover state
explicitly that this does **not** prove arrival in the Outlook inbox, and BLK-01 stays open until
a human confirms a real message.

**Why:** It would be easy, and wrong, to treat a 200 from Resend as "email works". The whole
premise of this build is that the site never claims more than it can prove. The gap between
"accepted for delivery" and "in a human's inbox" is exactly the kind of gap that gets glossed
over, so it is documented in three places rather than assumed.

### D54. A dev-only endpoint override exists so the delivery path is actually tested

**Decision:** `RESEND_ENDPOINT_OVERRIDE` can point the adapter at a local mock. It is ignored when
`NODE_ENV=production`.

**Why:** Without a real API key there is no way to exercise status mapping, header handling and
payload shape. Refusing to test it would mean shipping a delivery path that had never run. The
production guard means the seam cannot redirect a live enquiry, and it is documented as a test
seam rather than an integration point so nobody mistakes it for one.

### D55. The confirmed trading address is recorded in code, not yet rendered

**Decision:** The founder supplied the real trading address on 2026-11-06 —
No 4, Adeoye Street, Ibadan 200109, Nigeria — with the stated position that transparency is a core
business value, and authorised its use on the website if needed. It is recorded in
`src/lib/site.ts` as `businessAddress`, and `PENDING_BUSINESS_DETAILS.registeredAddress` is marked
resolved.

**Why record it:** it is a confirmed fact, and it was already needed for the Brevo signup. Leaving
it in a chat transcript rather than the codebase would have lost it.

### D56. It is not published on the site yet, and that is deliberate

**Decision:** `businessAddress` is exported but **not rendered on any page**. The privacy policy
and Terms do not display it, and nothing in the UI changed.

**Why:** this is a residential street address. A signup form requires a billing address; a public
website does not. Publishing it would place a home address in every search index permanently, and
it is the kind of decision that should be made once, deliberately, with the trade-off stated —
not made implicitly because a provider's form asked for it.

**What is not being done:** nothing is being concealed. The site already states plainly that the
business `operates remotely from Nigeria and is not aligned to US business hours`, and the address
is supplied to the email provider and available on request. The privacy policy's outstanding
address item is about the **legal entity**, which is still undecided (LR-01) — a street address is
not a substitute for it.

**If the founder wants it published**, the change is one line in the footer or the legal pages.
That is a separate, explicit decision. Publishing is not the default.

### D57. Contacting Brevo support is authorised, after an earlier decision not to

**Decision:** the founder reversed the earlier instruction. A support ticket **may** be raised with
Brevo, specifically to resolve account validation by SMS.

**Why this changed:** the original instruction was made when the question was *"will this provider
accept our domain?"* — a pre-sales question that email research could answer. The current problem is
different in kind: a code that never arrives on a Nigerian (+234) mobile number. Brevo's own community
forum contains a thread on exactly this failure, and in every resolved case the account had to be
validated manually by staff. There is no self-service route around it.

**This is not a re-opening of provider selection.** Brevo has accepted the domain, issued correct
records and authenticated it. The blocker is account validation, not the provider's suitability.

**Constraints that still apply to the ticket:**

- Do **not** accept a paid upgrade in order to obtain support. The screenshot showing
  *"Phone support is available on the Professional plan"* is not a reason to buy a plan — the ticket
  form itself is available on free.
- Do **not** use a purchased virtual or disposable number to pass verification. It breaches Brevo's
  terms, and it would leave account recovery tied to a number the founder does not control.
- **No secrets in the ticket beyond the minimum.** Phone number, account email and support ID are
  required; the API key never is.

**If the ticket fails**, the fallback remains Zoho ZeptoMail, with the caveat already recorded that it
also requires manual account review — so it may substitute one waiting room for another rather than
removing it.
